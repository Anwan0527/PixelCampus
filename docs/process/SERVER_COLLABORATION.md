# 服务端协作指南：别人怎么改服务端（新功能 / 新字段）

> 前提（见 [ADR 0001](../adr/0001-public-private-split.md)）：服务端 `server/` 不在公开仓库里。本文说明**别人想参与带服务端的功能时怎么做**，以及改服务端代码和存档字段时必须遵守的规则。

## 一、三种协作方式（按信任程度）

### A. 默认：协作者只改公开仓库，服务端那一半由主人实现（推荐大多数人）
1. 先写 `docs/feature/<日期-名称>/spec.md`（需求）→ 主人确认 → 再写 `plan.md`（计划，里面写清**协议改动和存档字段**）。
2. 在公开仓库里做：`src/shared/<功能>.ts`（规则写成**纯函数**，带单测）、`src/shared/protocol.ts`（新消息 + 注释）、客户端界面。
3. 把「服务端要做什么」写成清单放进 plan.md 或 PR 说明：新消息的处理流程（校验什么、改哪些档案字段、回什么消息）、每日上限 / 冷却 / 位置要求。因为规则已经在 `shared/` 里，**服务端 handler 很薄**：取档案 → 调用 shared 规则 → 落盘 → 回消息。
4. 主人合并 PR 后实现服务端 handler、联调、部署。协作者用 `?offline` 单机模式验证客户端部分。

### B. 受信任的服务端协作者：授权访问私有服务端仓库（需要主人批准）
适合长期、固定的合作者。流程：
1. 主人在私有仓库给对方 **write** 权限（只给服务端仓库，不给服务器 SSH、部署脚本、口令）。
2. 对方同时 clone 公开仓库和私有服务端仓库，**并排放好**：服务端代码放在公开仓库的 `server/` 目录里（这个目录已在公开仓库的忽略列表里，不会误提交）。
3. 本地联调：`npm run server`（8787，默认存档在 `data/server/`，可用环境变量 `DATA_FILE=.cache/dev/players.json` 指到临时位置；管理员口令哈希用 `ADMIN_KEY_HASH` 设成自己的测试值）+ `npm run dev`（5173，Vite 把 `/ws`、`/up`、`/img` 代理到 8787）。
4. 开分支 → 改 → 本地 `npx tsc --noEmit -p .` + `npx vitest run`（含服务端测试）全过 → 向私有仓库提 PR；改了 `src/shared/*` 的部分另提公开仓库 PR，两个 PR 在说明里互相链接。**主人审核合并，部署永远只由主人做。**
5. 现状说明：服务端目前是靠一个「私有备份仓库」跟踪同一工作目录里的 `server/` 等文件（主人用 `docs/private/pgit.sh` 同步），它能备份但**不适合多人协作**。要做 B，建议先把 `server/` + 服务端测试整理成**独立的私有仓库**（含 CI：先检出公开仓库，再把服务端放进 `server/`，跑类型检查和测试），再邀请协作者——这件事需要主人决定后再做。

### C. 开放一个最小可运行的参考服务端（暂不推荐）
把服务端的接口 + 空实现放进公开仓库，让任何人能完整跑通联机。代价是要长期维护一份「去掉规则细节」的版本，且会暴露协议之外的服务端行为，目前不做。

## 二、改服务端 / 加字段必须遵守的规则

### 1. 存档字段（玩家档案 `Saved`）
- **新字段一律可选**；在 `src/shared/<功能>.ts` 写 `cleanXxx(raw)`（校验类型、截断长度、丢弃非法值），读档时过一遍：旧档案缺字段、被篡改的值都不会报错。
- **默认值不落盘**（没动过的玩家不占空间）；字段名尽量短——档案有上万份，每份在内存里约 2~8KB，新增字段要估算体积（写进 spec 的「性能与成本」）。
- **不改已有字段的含义**。必须改时：加版本标记（如 `v`）、读取时升级、用「老档案样本」写迁移测试；上线前用线上完整备份跑一遍重放（主人做）。
- 新的数据文件（如 `place.jsonl`）要写进 plan 的「备份清单」，并在 FEATURES / CHANGELOG 注明。

### 2. 协议（`src/shared/protocol.ts`）
- 新消息加在联合类型里并**写一行注释**（它会成为 [PROTOCOL.md](../architecture/PROTOCOL.md) 的说明），然后 `npm run protocol:doc`（有测试检查）。
- **向后兼容**：新增可选字段、新增消息不需要改 `PROTOCOL_VERSION`；会让旧客户端出错的改动才升版本——升版本会让所有在线玩家被提示「客户端版本过旧，请刷新页面」，要在 plan 里写明。
- 服务端在对应的 `server/handlers/<功能>-handler.ts` 的 `register(d)` 里登记「消息类型 → 处理函数」（限流 `limit`、是否打断牵手 `breaks` 是登记时的标志位）；重复登记启动即报错。

### 3. 校验与安全（信任模型：客户端只上报「想做什么」）
- 位置、冷却、每日上限、权限、价格、概率全在服务端；玩家文字用 `cleanText` + 敏感词过滤；需要审核 / 举报的内容走现有的审核与举报流程；管理员操作写审计日志。
- 不得在客户端之外信任任何数值；不得把真实 IP、口令、令牌写进日志或回给客户端。

### 4. 测试
- 规则 → `tests/<功能>.test.ts`（公开，纯函数）；服务端集成 → `tests/<功能>-server.test.ts`（真起服务器 + ws 客户端，仿 `tests/place-board.test.ts`；这类测试只在有服务端的环境跑）。
- 提交前：`npx tsc --noEmit -p .` 和 `npx vitest run` 全过；改了协议要 `npm run protocol:doc`；改了钓鱼规则要 `npm run guide`。

### 5. 性能与成本
- 估算新增的 CPU / 内存 / 磁盘 / 带宽；全表扫描（遍历所有玩家档案）要说明频率和代价（冻结的档案会被临时解析）；列表要分页、有上限；图片 / 文件走流式、有总量上限。

### 6. 上线
- 改了 `src/shared/*` 必须**前后端一起部署**；部署前备份玩家数据；新增 nginx 路由 / 请求体大小等运维改动写在 plan 的「上线计划」，由主人执行；部署后看页面哈希、服务状态、`/healthz`、日志。

## 三、协作者清单（改动带服务端时，PR 说明里逐条确认）
- [ ] 有 spec + plan（含协议 / 字段 / 备份 / 上线说明）
- [ ] 新字段可选 + `clean` 函数 + 迁移 / 兼容说明
- [ ] 新消息有注释、`protocol:doc` 已更新、是否升 `PROTOCOL_VERSION`
- [ ] 服务端校验（位置 / 冷却 / 上限 / 权限 / 文字清洗）都有
- [ ] 测试（规则 + 服务端）全过，`tsc` 无报错
- [ ] 性能 / 内存 / 磁盘估算写了
- [ ] FEATURES / CHANGELOG 已更新
